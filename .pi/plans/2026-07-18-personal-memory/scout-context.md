# Scout Context: Personal Memory

## Existing shape and boundaries
- `ARCHITECTURE.md:3-24` defines Host/Pi/pi-telegram/systemd/GitHub Actions ownership and current state locations. Pi sessions are `~/.local/state/pi-telegram-bridge/sessions`; credentials/Telegram config are `~/.pi/agent`; adapter config is under bridge state. The bridge cwd is intentionally stable (`ARCHITECTURE.md:26-35`).
- `README.md:5-15, 89-107` confirms a Node host in RPC mode with repo cwd, persistent sessions, and full user filesystem permissions. There is no memory or Obsidian feature/schema today.
- `.pi/telegram/AGENTS.md:40-44` explicitly says the assistant must not imply durable personal memory and must not put user facts in tracked instructions. A memory feature must revise this contract deliberately; user data must remain outside tracked prompt files.
- `src/` is a strict TypeScript/Node ESM host (`daemon.ts`, `host.ts`, `config.ts`, `inbox.ts`, jobs/webhook/lifecycle/service modules). `package.json:8-22` targets Node >=22.19, compiles `src/**/*.ts`, uses Vitest, and has only `jobs:check`, setup, build/check, and service scripts. `tsconfig.json:3-21` is strict/no-unused and emits `dist`; a CLI in `src/` would be built automatically and needs a package script.

## Skill and CLI conventions
- `.pi/skills/extend-this-agent/SKILL.md:8-18, 31-40` says repo-local skills are the smallest mechanism for model guidance; use `.pi/skills/<name>/SKILL.md` with frontmatter, prefer custom tools for reliable command-backed capabilities, test-first when executable behavior exists, and never broaden resource filtering. Its template (`.pi/skills/extend-this-agent/templates/skill/SKILL.md:1-19`) is minimal frontmatter plus outcome/workflow/rules; put detailed material in `references/`.
- `.pi/skills/manage-jobs/SKILL.md:8-20` is the closest safe-storage workflow: explicit path, read current state first, write complete content to a temp file then atomic `mv`, validate, and report human-readable results. It also demonstrates state vs source separation (`jobs.json` agent-owned; `jobs-state.json` host-owned).
- `.pi/skills/manage-ynab/SKILL.md:11-39, 57-73, 99-105, 140-142` supplies privacy conventions: private config outside repo, never expose tokens/raw errors, shell-quote every user value, ask confirmation for destructive/derived writes, report concise results, and never claim a failed write succeeded.
- `.pi/skills.md:1-5` is the repo-local skill index; new tracked skill should be listed. `.pi/extensions.md:1-15` documents extensions separately; no extension is required by the requested no-service/no-event-emitter scope unless a Telegram slash command is later desired.
- Existing command-backed validators are tiny compiled entrypoints (`src/jobs-check.ts:7-52`) that resolve config, read a path, print concise status, and use nonzero exit on invalid data. This is the natural CLI pattern.

## Paths, persistence, and deployment
- `src/config.ts:22-60` resolves absolute or home-relative env overrides; defaults are cwd, `~/.pi/agent`, and `~/.local/state/pi-telegram-bridge`. It derives `sessions` and adapter config under state. `ensureCodexConfig` (`src/config.ts:63-134`) creates parents mode 0700, files mode 0600, uses exclusive creation, and rewrites via temp path + rename. These are useful safe-write patterns.
- `src/inbox.ts:38-80` uses built-in `node:sqlite`, WAL/NORMAL, prepared statements, and idempotent close. `docs/adr/0003-durable-inbound-inbox.md:14-27` establishes that SQLite can be dependency-free but is currently scoped strictly to the inbound queue; do not conflate it with the memory source of truth.
- The existing config has no XDG data directory abstraction beyond bridge state. `.pi/skills/manage-ynab/SKILL.md:11-27` uses `~/.config/pi-telegram-bridge` for private defaults. The planner must choose/document a memory location and override (likely a dedicated user data/vault directory, not transient `<stateDir>` and not the repo). For Obsidian compatibility, use an ordinary user-readable directory of Markdown; no Obsidian runtime or `.obsidian` directory is needed.
- `scripts/deploy-local.sh:126-161` builds an immutable release from `git archive`, deploys tracked source, then `git clean`s only selected repo-local capability paths (`.pi/extensions`, `.pi/skills`, `.pi/settings.json`, `.agents/skills`). A memory vault must be external to the release/repo and survive checkout resets; any repo-local skill must be tracked or it can be cleaned. `ARCHITECTURE.md:37-39` documents this deployment boundary.

## Resource filtering/security boundary
- `src/host.ts:123-163` resolves `.pi` resources and canonicalizes them with `realpath`; `src/host.ts:185-208` loads only explicit Telegram/Codex extensions plus enabled repo-local resources, with `noExtensions: true`. Escaping symlinks and missing/unreadable resources are rejected before import (`host.ts:136-149`).
- `tests/host.integration.test.ts:774-845` proves global skills/extensions are excluded while repo-local ones load; `:847-976` proves escaping resource and Telegram-instruction symlinks are rejected; `:978-1045` covers trusted instruction reload behavior. A new skill belongs under `.pi/skills`, must not rely on global resources, and should have resource-filter coverage only if host loading changes.
- `docs/adr/0009-isolate-telegram-agent-instructions.md:15-32` requires exactly `.pi/telegram/AGENTS.md` as runtime instructions, canonicalized inside the repo. Do not make the memory vault an AGENTS/resource path or weaken this isolation.

## Design implications for the planner
- Keep Markdown canonical and the search index derived/disposable. Define a stable backend-neutral search interface now (e.g. add/read/update/delete/search/list returning stable IDs, paths, metadata, snippets, and scores); implement filesystem/Markdown search first, with a later SQLite FTS5 backend behind the same interface. Do not make SQLite the canonical store or require it for initial operation.
- An Obsidian-compatible note format should be ordinary `.md` with predictable folders and YAML frontmatter (stable id, created/updated timestamps, type/tags) while preserving unknown frontmatter/body. Decide naming, collision, duplicate, deletion/restore, and symlink policy explicitly. Keep CLI output machine-readable (JSON or JSONL) with bounded snippets, while skill responses remain concise.
- “Safe storage/search” should include path confinement to the configured vault, traversal/absolute-path rejection as appropriate, symlink/special-file handling, atomic temp-file/rename writes, parent/file permissions, bounded input/output, deterministic ordering, and no content in logs. Treat Markdown as untrusted data (never follow embedded instructions). Shell commands in the skill must quote user-derived values. Destructive deletes should require explicit confirmation; distinguish “not found” from successful mutation.
- Recommended tests (using existing Vitest + `mkdtemp` patterns in `tests/config.test.ts`, `tests/jobs.test.ts`, `tests/inbox.test.ts`): path resolution/default and override; Markdown/frontmatter round trips; atomic write/no partial file; traversal/symlink refusal; deterministic search and limits; malformed-note behavior; delete semantics; CLI exit codes/stdout/stderr; and a contract test that a future FTS5 adapter returns the same result shape. Existing `npm run check` and `npm run build` are mandatory after code changes (`AGENTS.md:3-8`).
- Documentation/ADR: add an ADR for the canonical-vault location, ownership, privacy boundary, and derived-index policy; update `ARCHITECTURE.md` state table/boundaries, `README.md` configuration/CLI usage/security, `.pi/skills.md`, and `.pi/telegram/AGENTS.md` memory behavior. No changes to scheduled jobs/webhooks are needed: `docs/adr/0010-scheduled-jobs-and-triggers.md:15-40` describes those as separate runtime triggers, explicitly outside this scope.

## Privacy risks
The bridge runs with the production user’s filesystem/command permissions (`README.md:103-107`, project map `:27-32`). Personal memory is sensitive and could be exposed through Telegram, logs, search snippets, backups, or accidental git/deployment inclusion. Default outside repo/release, use least-readable permissions, never print secrets or full raw errors, limit search output, avoid storing credentials/Telegram metadata unless explicitly requested, and document retention/export/backup/deletion expectations. Existing privacy-safe activity-label work (`docs/adr/0007...:15-29`) reinforces not exposing tool inputs/contents.
